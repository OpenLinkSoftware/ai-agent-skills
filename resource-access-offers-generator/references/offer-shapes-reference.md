# Offer Shapes Reference
Every Offer below also requires its own `skos:related [ oplpro:hasFamily <family IRI> ]` (blank node, `sh:nodeKind sh:BlankNode` enforced) — `product_family/loac#this` for File/Graph Access, `product_family/opal#this` for API Access/Chat Service. This is separate from any `skos:related` already required on the Product/License (those are always plain IRIs, `sh:nodeKind sh:IRI`). See SKILL.md "Auto-Derivation" → "offer-level product family".
## File Access Offer
Product: schema:WebAPI, category "File Access", endpoint /DAV. License: opllic:uriParameter 1..1. Offer: DAVOffer + DemoFileAccessOffer, OfferGroupFileAccess, skos:related family `loac`.
## Graph Access Offer
Product: schema:WebAPI+Service, category "Data Access", endpoint /sparql. License: opllic:graphParameter 1..1. Offer: DemoGraphAccessOffer, OfferGroupGraphAccess, skos:related family `loac`. Also requires an oplacl:ConditionalGroup + acl:Authorization block in the same file granting oplacl:Read on the exact graphParameter graph IRI — see SKILL.md "Graph Access Authorization Block".
## API Access Offer
Product: schema:WebAPI (full OPAL Chat API template — serviceType, hasPart EntryPoint, top-level potentialAction CommunicateAction, skos:related to OPAL server, documentation/exampleOfWork), endpoint /chat/api. Exactly 4 tiers sharing one Product (Entry $0, Medium $9.99, Advanced $19.99, Max $49.99), each its own Offer/License/PriceSpecification. License: no uriParameter/graphParameter; skos:related to OAuth applications page. Offer: skos:prefLabel required, OfferGroupApiAccess, skos:related family `opal`. Paid tiers (non-$0.00) require oplofr:interval/intervalCount. A sh:sparql completeness gate on the Product requires all 4 tier-typed Offers to exist (Entry/Medium/Advanced/Max) before the file conforms. See SKILL.md "API Access Product Description Template + 4-Tier Offer Structure".
## Chat Service Offer
Product: schema:Service (shared `{host_short}OPAL#this`, NOT tied to a specific resource — no License resource IRI input), category "AI Agent Platform", 4 required hasPart sub-endpoints (Chat, Assist-Metal, MCP Streamable HTTP, MCP SSE) each with a fixed serviceType literal, gate-enforced via qualifiedValueShape (not a rigid count, so a 5th endpoint won't break it). Open-ended multi-family structure (e.g. Data Twingler, Support Assistant, generic BYOK/Max), each typically 4 tiers, all sharing one Product. License: no uriParameter/graphParameter, no skos:related requirement (unlike API Access). Offer: skos:prefLabel required, OfferGroupChatService, skos:related family `opal`, no schema:url on the Offer itself. No completeness gate for the multi-family structure (available as a future follow-up, like Graph Access's authorization block and API Access's tier gate were). See SKILL.md "Chat Service Product/License/Offer Description Template".
