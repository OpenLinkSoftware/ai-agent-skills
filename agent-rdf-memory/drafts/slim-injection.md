## How it targets the designated store

Every section is a SPARQL result. The query text is the same for both store
kinds; only the graph base changes.

- **Endpoint.** Graph base `urn:dav:/DAV/home/kidehen/agent-rdf-memory/`, run
  through `load_memory.py`'s existing authenticated `sparql_csv()`.
  `slim_injection.py --print-queries --graph-base <base>` prints the text.
- **Filesystem.** The local Turtle files are loaded into an rdflib Dataset with
  one named graph per file, so the `GRAPH` clauses match. Loading the three core
  files took 0.1 s.

One constraint: rdflib refuses to resolve relative IRIs against a `urn:dav:`
base, so the filesystem path uses the store's own directory as the graph base.
The output hides the difference behind `mem:`. `session-graph-gate.py` already
works around the same limit.

## Defects found in the current loader and store

These hold whether or not the slim injection is adopted.

Update, later on 2026-11-11: defects 1 and 2 are fixed in `load_memory.py`, along
with a third found in testing (a result containing the text "SPARQL compiler" was
treated as an error). Defects 3 and 4 are data and sync problems and remain. The
byte counts in this document describe the loader before those fixes.

1. **The intent sample is hard-coded.** `load_memory.py` line 464 always queries
   `VirtuosoSparqlTroubleshooting`. Its six OPTIONALs multiply out to 20 rows
   that carry about nine distinct facts.
2. **The step index is the oldest 80 steps.** The query orders by position and
   stops at `MAX_STEPS`. Steps numbered above that never reach a session. Six of
   the 86 lines are duplicates, one per extra `rdfs:seeAlso`.
3. **The endpoint's index graph was a month behind.** The injection's newest
   session was position 1190 (2026-10-08). The local `index.ttl` is at 1248
   (2026-11-10).
4. **Intent routing reaches about half the steps.** 170 of 356 steps are attached
   to no topic howto. Four topics have no intent. Six of the seven intents name
   no required howto.

## Decisions for you

1. **The always-on list.** I picked the eight. A marker triple on each step would
   make the list data, not code; that needs a new ontology term, which I have not
   minted.
2. **Whether the full-read mandate stays.** The gate box, `AGENTS.md`, the global
   `CLAUDE.md` and `check-memory-gate.py` all require reading `core.ttl`,
   `preferences.ttl`, `ontology.ttl` and `index.ttl` (805 KB together). The slim
   index can ship under that mandate unchanged. Replacing the mandate with
   "index, then pack" is a protocol change to those four places.
3. **The 170 unrouted steps.** Assign each to a topic, or keep the phrase match.
   The phrase match is crude: it reaches 94 of the 170, misses 76, and short
   phrases such as "RDF" and "skill" pull in loosely related steps.
4. **Who pulls the pack.** The agent can run it after reading the first prompt,
   or a prompt-submit hook can classify and inject it. The hook is deterministic
   but classifies on trigger phrases alone.
5. **The purpose sentence.** The wording is mine.

## Not verified

- No query was run against the endpoint. The prototype never touches
  credentials. `IRI(REPLACE(...))` in the pack query is standard SPARQL 1.1 but
  untested on Virtuoso.
- The always-on step IRIs resolve today; nothing guards against a rename.
- `core.ttl` and `preferences.private.ttl` are not queried by the draft, so the
  private endpoint order is absent from it.
