How it works

Three steps from any ODBC or JDBC database to a knowledge graph

Attach

Connect Virtuoso to any DBMS it can reach over ODBC or JDBC; the showcases use Microsoft SQL Server, PostgreSQL and Databricks alongside native Virtuoso SQL tables as examples. The tables appear inside Virtuoso, for example "sqlserver"."northwind"."customers", and the data stays where it is.

Map

An RDF View gives each row a hyperlink of its own, such as …/customers/CustomerID/ALFKI#this, and turns each foreign key into a link you can follow. That hyperlink is a super-key that works on any platform able to follow a link.

Query or ask

Use SQL, SPASQL or SPARQL, browse by facets, or put the question to an OPAL agent. Every IRI also opens a page that describes it.

Ontology generation

Your schema becomes an ontology. Shared ontologies make it travel.

When Virtuoso generates an RDF View, it also generates the ontology that describes it: a class for every table, a typed property for every column, a link for every foreign key. Align those classes with shared ontologies such as FOAF, schema.org or DBpedia, and one question in a shared vocabulary reaches every database at once.

Why it matters

Three facts worth knowing before you choose

Fact 1

Nothing is copied

Each SPARQL query here is translated into SQL and run against the source tables at that moment. When a row changes in the source database, the next answer changes with it. There is no export to schedule and no copy to drift.

See it on Northwind →
Fact 2

Every row's hyperlink is a cross-platform super-key

Each customer, order and product gets a hyperlink that opens a page describing it. Unlike a primary key, it keeps its meaning outside its own database, so rows in two different databases, or a row and a web page, can be joined by reference instead of by file transfer.

See sponged entity links →
Fact 3

Answers come from queries, not from a stored copy

An OPAL agent builds its answer from a query you can inspect. When a number looks wrong, you can see exactly where it came from.

Access control

Your data stays where it lives. So do the rules.

Access is decided by attribute-based (ABAC) ACLs on the server, not by the page. On the demo instance anyone may run SPARQL; SQL, SPASQL and fresh sponging need a sign-in. Identity can come from WebID-TLS, OAuth or OpenID Connect through the Virtuoso Authentication Layer.

Virtuoso Sponger

Point it at a web page. Get back a graph.

The Sponger is Virtuoso's Linked Data middleware. Its cartridges read a web resource (an HTML page, an RSS feed, a GitHub repository, an X profile), produce RDF, and store it in a named graph whose IRI is the source URL. On URIBurner, a query names that graph with FROM <url> and adds DEFINE get:soft "replace" to fetch or refresh it.

Two sources. The first four examples query the graph the Sponger built from Techmeme's RSS feed; the last queries the graph it built from the ai-agent-skills GitHub repository. Each graph is named by its source URL. How they run: Fetching a new or stale URL needs a signed-in session on URIBurner, so each card runs anonymously against the graph the Sponger already built, and offers a Re-sponge link that adds DEFINE get:soft "replace" and opens URIBurner's authenticated endpoint.

OPAL · OpenLink AI Layer

      
An assistant that answers from live queries

      
OPAL connects LLMs to databases, knowledge graphs, filesystems and APIs. An agent is a set of instructions plus a list of query functions. The model picks a function, Virtuoso runs a predefined SQL, SPARQL or SPASQL query, and the answer is built from what comes back. Because the agent and the data are only loosely coupled, you can change the model or the Data Space without rewriting the agent.

Ontology generation

      
Ontologies generated from your SQL schema, then reused with shared ones

      
An RDF View is two things: the mapping that turns rows into entities, and an ontology that describes them. Virtuoso generates both from the database schema, on the fly, for any ODBC- or JDBC-accessible DBMS. Every class and property gets its own IRI, so the ontology is itself linked data you can query, describe and extend.

    

    
What gets generated

    

      
Table
becomes a class
Demo.demo.Products becomes …/schemas/Northwind/Products, labelled with its source table.

      
Column
becomes a typed property
UnitPrice becomes an owl:DatatypeProperty with domain Products and range xsd:numeric.

      
Foreign key
becomes a link
Products → Categories becomes the owl:ObjectProperty has_categories, so joins become paths you follow.

      
Alignment
connects it to shared ontologies
One rdfs:subClassOf or owl:equivalentClass statement ties a generated class to FOAF, schema.org or DBpedia.

    

    
See it on the live server

    
Each query below runs against demo.openlinksw.com. The first three read the generated ontologies; the last three show them aligned with, and answering in, shared vocabularies.

    

    
Generate one for your own database

    

      
Attach and generate
Link the tables over ODBC or JDBC, then generate the RDF View. Virtuoso writes the ontology (TBox), the instance mapping (ABox) and the rewrite rules that make each IRI resolve.

      
Align
State how your classes relate to shared ones (rdfs:subClassOf, owl:equivalentClass, owl:equivalentProperty), in a few triples kept beside the generated ontology.

      
Query in any vocabulary
Ask in your own terms or in the shared ones. Apply the alignment in the query, as the last example does, or let Virtuoso's inference rules do it.

    

    
Agent skills that automate these steps: virtuoso-support-agent (RDF View generation) and linked-data-skills (RDF Views from database objects).
